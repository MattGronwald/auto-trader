## 1. Spec gaps and contradictions (resolve before/while coding)

Ordered by how badly they bite if ignored.

| # | Issue | Where | Proposed resolution |
|---|---|---|---|
| G1 | **Exit orders vs. "Risk Engine is the only broker caller".** Position Manager (stops, time exits), kill (`close_all`) and dashboard flatten all need to submit orders. If they go through the full `check()`, a stop-out can be blocked by `max_orders_per_hour` or the daily loss pause. | §0.1, §4.5, §4.7 | Risk Engine gets two entry points: `check(OrderIntent)` for entries (all 11 checks) and `exit(ExitRequest)` for reduce-only orders (only checks: symbol has a position, qty ≤ position qty, mode matches). Exits are never rate-limited or paused, but still logged as `risk_decisions`. Risk Engine remains the sole holder of the `Broker` reference. |
| G2 | **Alpaca crypto likely has no bracket/OCO orders.** Then every stop is client-side, enforced by the Position Manager. A sleeping laptop = no stop, even in paper. | §4.5 last para, §4.6 | Verify in Phase 0. Assume client-side stops as the default path. Treat "core process down" as a first-class risk: alert + reconcile on restart, and run paper on an always-on host earlier than Phase 5 if overnight runs matter. **0.7 (2026-10-11): confirmed.** Crypto supports market/limit/stop-limit only; no bracket/OCO/OTO/trailing. Client-side stops are the design; a broker stop-limit as backup is a WP 1.5 decision. |
| G3 | **Expectancy check has no prior in Phase 1/2.** `p_win_est` is capped at "historical win rate + 10 pp" — no history exists at start. Units are also mixed (price distance vs. fee). | §4.5 #11 | Add `risk.default_win_rate_prior` (e.g. 0.45) used until `n ≥ min_trades_for_evidence`. Compute everything in quote currency for the computed qty: `qty·(tp−entry)·p − qty·(entry−stop)·(1−p) − fee(entry) − fee(exit) > 0`. Note: this lives in the human-only `risk` block. |
| G4 | **Sizing formula is ambiguous** (`size_fraction × that` inside a `min`). | §4.5 #7 | `qty = size_fraction × min(risk_qty, cap_qty, broker_max_qty)` → round down to lot size → reject if `< broker_min`. Property tests encode exactly this. **1.3:** plus a cash cap `cash / (entry × (1 + taker))` (D14). |
| G5 | **Timeframe mismatch.** Profile uses `trend: 4h`; feed only maintains 1m/5m/15m/1h. Alpaca crypto stream delivers 1m bars only. | §4.1, §6 | Feed resamples from 1m to all timeframes listed in the profile (derived set, not hard-coded). Backfill depth = max indicator lookback × largest TF (≈ 50 × 4h ≈ 9 days of 1m bars), at least 25 h (longest civil day, DST) plus a bucket for the day-anchored VWAP (D12). |
| G6 | **"Day" undefined for a 24/7 market.** Daily loss limit, daily budget, orders/day, reviewer schedule. | §4.5 #3, §6 | One config key `trading_day_tz` (default `UTC`), boundary at 00:00. Reviewer runs at 03:00 Europe/Berlin as specified, independently. |
| G7 | **Unsafe expression evaluation.** `signal_rules[].expr`, `score`, `promote_if`, `applies_to` are strings. `eval()` is not acceptable. | §6, §8.2 | One shared, whitelisted AST evaluator (names = feature dict, ops = arithmetic/compare/bool/`min`/`max`/`abs`, `[-n]` = lag access, `in a..b` for ranges). Validate all expressions at profile load, fail fast. **Done in 0.2** (`core/expr.py`): names checked against vocabularies in `core/features.py`; `**`/`%` excluded (DoS); numbers must be finite; statically wrong result types (predicate vs. score) rejected at load. Glob matching (`rule_id == breakout_*`) is not supported yet — add in 4.1 if `applies_to` needs it. |
| G8 | **Kill file across containers.** Core and API are separate compose services; `touch KILL` must be visible to both. | §4.11, §11 | `KILL` lives in a shared volume (`/data/control/KILL`); path from config. Core additionally polls `control_state` in DB. |
| G9 | **Model IDs.** `claude-haiku-latest` / `claude-sonnet-latest` are not real aliases. The price table must match exact IDs. | §6 | Pin exact model IDs in the profile; price table keyed by model ID in `config.yaml`, versioned. Verify current IDs/prices at Phase 2 start. **0.2:** profile pins `claude-haiku-5-5` / `claude-sonnet-5-5`; IDs containing `latest` are rejected at load. Price table deferred to 2.1. |
| G10 | **Alpaca crypto fee mechanics.** Fees on buys may be deducted from the received asset qty → position qty ≠ ordered qty → false reconciliation mismatches. | §4.6, §4.7 | Verify in Phase 0; reconciliation compares against broker-reported qty, Position Manager adopts broker qty after fill. **0.7 (2026-10-11): confirmed and worse.** Fee is charged on what you receive (buy → in the coin, sell → USD) and posted **end of day** as a `CFEE`/`FEE` activity; fills don't carry it. → Reconciliation adopts broker qty and tolerates the expected fee (1.5); exits sell the actual position qty (1.6); journal records an estimated fee and replaces it with the posted `CFEE` (3.1). See `docs/alpaca-notes.md`. |
| G11 | **Stale data + client-side stops.** "Position Manager still runs on last known price" means the stop is effectively off while stale. | §4.1 | Stale > N s with an open position → alert; stale > M s → market-exit via `exit()` (configurable, default on in live). |
| G12 | File name: layout says `spec.md`, repo has `SPEC.md`. | §11 | Keep `SPEC.md`. Trivial. |
| G13 | **Sparse venue data (found 2026-10-11).** Alpaca crypto: many minutes without a bar (SOL ~50 %), quotes only on book changes, tiny volume. "No data for N s" can't separate a broken feed from a quiet market, and `vol_z` on this volume is suspect. | §4.1, §4.2, §6 | Feed health is connection-level; per-symbol price age with a REST refresh before declaring stale (D11). Higher TFs are finalised only after a REST check of each window (stream bars are pending until then), with flat fills for empty buckets. Judge ETH/SOL usability in WP 1.7 with `feed.density` logs; consider a different universe or venue if signals are noise. **Observed 2026-10-11:** with `stale_alert_s: 60` the price-age check flaps (6 stale/fresh pairs per 6.5 min across 3 symbols); consider raising it (e.g. 180 s) before the scanner relies on it. **Density by time (8.5-day backfill):** weekday coverage BTC 98 % / ETH 55 % / SOL 67 %, weekend about half, peak 13–16 UTC. → In WP 1.7 evaluate signals per hour and weekday/weekend, not as one average; a time-of-day/weekend filter (or limiting ETH/SOL to busy hours) may matter more than the indicators. |
| G14 | **Concurrency caps can't be exact in the Scanner (found 2026-10-11).** Bars of all symbols close together, so several `CandidateSignal`s go out before the Cycle Runner has created any cycle row; a Scanner-only check of `max_concurrent_cycles` / open cycle per symbol can be exceeded. | §4.2, §4.3 | Scanner check is a cheap pre-filter on persisted state; the Cycle Runner (1.4) enforces both caps authoritatively when it creates a cycle, in the same transaction, and drops the excess candidate with a logged reason (D13). |

## 2. Tech baseline (Phase 0 decisions)

- Python 3.12, **uv** for env/lock, `src/` layout, ruff + mypy (strict on `risk/`, `broker/`, `core/`), pytest + hypothesis + pytest-asyncio, coverage gate on `risk/` = 100 % branches.
- SQLAlchemy 2.x async (`aiosqlite` dev, `asyncpg` prod), Alembic with `render_as_batch=True` (SQLite ALTER limitations). JSON columns via SQLAlchemy `JSON` type (portable).
- Pydantic v2 for all domain types; shared between core, API, and agent schemas.
- structlog JSON, `cycle_id` bound via contextvars.
- `alpaca-py` for REST + WS; `anthropic` SDK directly, no agent framework.
- Money/qty: `Decimal` in Risk Engine, broker adapter and journal; floats only inside indicator math.
- Single asyncio process for core; API as separate process reading the same DB and writing `control_state` + kill file.
- CI: GitHub Actions — ruff, mypy, pytest (unit + SimBroker integration with recorded fixtures), `pip-audit`.

| D12 | Indicator definitions (WP 1.1) | **2026-10-11, owner:** EMA 9/21/50: alpha = 2/(n+1), seeded with the first close, no adjust. RSI 14 and ATR 14: Wilder smoothing (alpha = 1/n). Donchian 20: rolling max high / min low **including** the current bar (the spec's example rule uses `donchian_high_20[-1]` for the prior channel). `vol_z`: (volume − rolling mean 20) / rolling population std 20; zero std → NaN, not inf (G13 sparse volume). Constant windows are detected exactly (max = min), since float rounding otherwise leaves a tiny std and a fake z of ±1 (PR #11 review). VWAP: cumulative, **anchored at the trading-day boundary** (D5: 00:00 UTC), not rolling. Lookbacks stay ≤ `MAX_INDICATOR_LOOKBACK` = 50. **Implementation details (WP 1.1, 2026-10-11):** Wilder averages are seeded with the SMA of the first n inputs (TA-Lib style; ATR's first true range is high − low). | D15 | Cycle Runner (WP 1.4) | **2026-10-11, owner (design approved; spec `docs/superpowers/specs/2026-10-11-cycle-runner-design.md`, revised after three spec reviews):** the `CandidateSignal` handler only admits (closing flag, freshness = Scanner's obsolete-bar rule, gate, then under the admission lock: open-cycle caps (G14) and open entry order on the symbol; insert), one asyncio task per cycle. "One cycle per candidate" holds for the at-most-once, non-replaying bus; no durable candidate id. Skip = `REJECTED`, no SKIPPED state. Edges taken only by WP 1.5 reconciliation: `SUBMITTED` → `EXPIRED`, `RISK_CHECK` → `FILLED`/`EXPIRED`; reconciliation → `FILLED` on any fill (full or partial, details carry `filled_qty`/`ordered_qty`/`partial`), → `EXPIRED` only on a final status with filled qty 0. Freshness re-checked on entering `RISK_CHECK` (stale → `EXPIRED`). `check()` called once, never retried, no per-step timeout. After submit only proven outcomes are mapped: `filled` → `FILLED`, `rejected`/`not_submitted` → `REJECTED`; `new`/`unknown`/`canceled` stay `SUBMITTED` (an IOC `canceled` may have partly filled) until WP 1.5 decides from the broker's filled qty. Orders are reconciled by order row, not cycle state: an `ERROR` cycle can own a real `pending` order (ack write failed after acceptance); it keeps reserving symbol + position slot (check 5, admission) but not a cycle slot. State update + `CycleTransitioned` event (field `details`, not `payload`) in one transaction via `EventBus.publish_tx(build, verify)`: `build` writes, flushes and returns the event (or `None` = drop), so admission's event carries the new `cycle_id`; commit + enqueue run in a bus-owned task under the bus lock (event-id order = delivery order) that survives caller cancellation; a commit exception triggers one read-back via `verify`: only a positive read-back confirms (→ deliver); a negative or failed one is `CommitUncertain` (a lost-ack commit may still land later), the cycle is logged stuck with no fallback write, and **any `CommitUncertain` suspends admission until restart** (`recover()` reads the final state), so a late-landing insert can't break G14. Exactly-once delivery holds for confirmed commits only; uncertain/abandoned units may be persisted undelivered. After `check()` a failed transition write leaves the last committed state (`RISK_CHECK` or `SUBMITTED`). `SUBMITTED → FILLED` is shared (runner on an immediate `filled` ack, WP 1.5 on reconciliation). Shutdown: `runner.close(budget_s)` bounds the whole call: `closing` set without the admission lock (admission re-checks it after commit and starts no task), cancel pre-`check()` tasks, drain shielded `check()` until the deadline minus `cancel_wait_s`, force-cancel, wait until the deadline, then report abandoned tasks; `bus.close(budget_s)` bounded likewise; in `run core` the runner closes before the bus drains. In-process shutdown is best-effort bounded; the hard deadline is process-level (second signal / `shutdown.timeout_s` watchdog → `os._exit(1)`, WP 1.5). Forcing is safe: the `pending` row is written before submit. Restart: open cycles before `RISK_CHECK` (or in it without an order row) → `ERROR`. Stub parameters are module constants (`agents/stub.py`); stop measured from `ask × (1 + slippage)` so the engine's rounded entry gives distance in [1.5 ATR, 1.5 ATR + tick). Not wired into `run core` until WP 1.5. One core process per journal. |
