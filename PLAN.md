## 2. Tech baseline (Phase 0 decisions)

- Python 3.12, **uv** for env/lock, `src/` layout, ruff + mypy (strict on `risk/`, `broker/`, `core/`), pytest + hypothesis + pytest-asyncio, coverage gate on `risk/` = 100 % branches.
- SQLAlchemy 2.x async (`aiosqlite` dev, `asyncpg` prod), Alembic with `render_as_batch=True` (SQLite ALTER limitations). JSON columns via SQLAlchemy `JSON` type (portable).
- Pydantic v2 for all domain types; shared between core, API, and agent schemas.
- structlog JSON, `cycle_id` bound via contextvars.
- `alpaca-py` for REST + WS; `anthropic` SDK directly, no agent framework.
- Money/qty: `Decimal` in Risk Engine, broker adapter and journal; floats only inside indicator math.
- Single asyncio process for core; API as separate process reading the same DB and writing `control_state` + kill file.
- CI: GitHub Actions — ruff, mypy, pytest (unit + SimBroker integration with recorded fixtures), `pip-audit`.

### 3.2 Position management and recovery acceptance (WP 1.5–1.6)

1. **Safe startup:** acquire the local single-writer lock, verify configured paper mode, recover cycles, reconcile broker orders/fills/positions, restore exit state and act on overdue exits, then allow admission. `recover()` alone only repairs cycle bookkeeping. Failure keeps entries disabled; protective exits remain available when broker position/mode can be established. WP 1.5 implements this with SimBroker, WP 1.6 enables Alpaca paper execution. Persistent account binding and cross-host/Postgres ownership remain 3.5 / pre-live work.
2. **Exit contract:** persist original stop, TP, initial risk, holding deadline and trailing high-water state. The current stub has no hold-time field: use `risk.max_hold_min` in Phase 1, then validate/clamp the Phase 2 agent request. Define executable trigger prices, multiple-trigger precedence, conservative same-bar stop/TP handling and dust behavior. Protect acquired qty immediately, including partial fills.
3. **Order/fill handoff and cycle completion (D15):** reconcile `pending`, `unknown`, `new` **and final statuses with unapplied fill/position effects**, regardless of cycle state. `_refresh_open_entries()` already writes `filled`/`canceled`; excluding those rows loses the handoff. Persist fill effects idempotently and retain conservative reservations until applied. For eligible non-terminal `RISK_CHECK`-with-order / `SUBMITTED` cycles, **any positive filled qty → `FILLED`**, full or partial (record `filled_qty`, `ordered_qty`, `partial`); **`EXPIRED` only on a final zero-fill outcome**. `canceled` alone proves neither. The existing runner still maps known immediate `rejected`/`not_submitted` outcomes to `REJECTED`; reconciliation uses D15's allowed edges. Never reopen an `ERROR`/other terminal cycle just to account for its order.
4. **Bounded resolution of uncertain or missing orders:** a `get_order` exception, including an order the broker no longer knows, fails new entries closed; it must enter this resolver rather than fail forever on every poll. Use client-id lookup for entries and complete, paginated symbol/side/time/qty history for id-less exits, excluding orders linked elsewhere. Link a uniquely identified match; ambiguous candidates require operator resolution. Transport/auth errors or incomplete history are not zero matches.

   WP 1.6 must enforce a **total transport deadline ≤ the engine I/O budget (currently 10 s)**, covering connect/read/retries and queued work; canceling `to_thread` alone is insufficient. Define finite adapter settings `order_visibility_allowance_s` (initial operational allowance **60 s**) and `order_resolution_timeout_s` (initial **80 s** from the original attempt: at most 10 s transport + 60 s visibility allowance + 10 s for the final lookup). Persist attempt/resolution state so restart cannot reset the bound. These are proposed local operational bounds, **not a verified Alpaca visibility guarantee**; document/validate broker behavior in 1.6.

   After transport completion + visibility allowance, a complete zero-match lookup may establish `not_submitted` **only if** the original worker is quiescent (no later local send/retry) **and** an authoritative broker contract/status rules out later acceptance or visibility. HTTP timeout alone does not establish the latter. A found order is reconciled normally. **By the resolution deadline**, unresolved absence, unavailable/incomplete history or ambiguous id-less matches become an explicit operator-required incident: alert, preserve `pending`/`unknown` and reservations, and do not blind-retry. This bounds automatic investigation rather than silently expiring a potentially real order. Operator resolution records evidence and the resulting order/position disposition before reservations are released. Only a broker-confirmed final outcome or proven non-submission reopens the affected path automatically. This supersedes D14's grace-window-only inference; the reviewer's time-only zero-match shortcut is intentionally not adopted without that broker guarantee.
5. **Retry and kill/flatten:** an exit may be **`not_submitted` because the budget expired before `close_position`**. The Position Manager must retry such a proven-unsent exit under a fresh bounded attempt after re-reading the position, free qty and other unresolved closes. `pending`/`unknown` exits first follow item 4. For kill/flatten, latch entries, cancel outstanding entry orders via the engine, reconcile races, issue audited reduce-only exits and handle late fills. Do not cancel protective sells as if they were entries. Report dust and uncertainty explicitly; “flat” requires no sellable holdings and no unresolved entry capable of filling. A SimBroker reservation test does not prove Alpaca retry behavior.
6. **Accounting required in Phase 1:** write positions and estimated fee-adjusted realized P&L on close so `strategy_trade_stats()` receives meaningful data. Preserve initial-risk denominator when trailing. Use bounded fee/rounding explanations; unexplained discrepancies pause entries. Posted activity reconciliation and richer metrics stay 3.1, with provisional/final provenance and stable identities to avoid double charging.
7. **Shutdown:** close admission, stop new feed work, drain/force-cancel the runner within its budget, drain the bus and release resources. Add the process watchdog/second-signal hard deadline. Persist abandoned work for recovery; forced cancellation is not proof broker work stopped. Fill identities are part of 1.5's interface/tests and implemented for Alpaca in 1.6.
8. **Local liveness (former 1.R4):** run kill/control polling independently of `feed.tick()`/REST refresh, using bounded supervised tasks. Hold an OS advisory lock on a journal-associated lock file for the core process lifetime (PID is diagnostic, not the exclusion mechanism). A second core fails startup; restart waits for the previous writer to exit and its SQLite work to resolve. Warn when the last `risk.snapshot_written` is older than **2 × the configured snapshot interval**; fail entry checks closed when required state is unavailable. Test hung feed refresh, second-core startup, stale snapshots and bounded shutdown. This is part of 1.5, not a separate infrastructure WP.

### 3.3 Strategy evaluation and evidence (WP 1.7)

The owner requested strategy alternatives for review; SPEC §16.1 proposes a BTC-only, slower-signal candidate with lower exposure and LLM spend. It is a proposal, not an approved replacement profile or a claim of profitability.

- Compare the current baseline and named candidate variants on the **same time-ordered data**, with identical fee, slippage and fill assumptions. Split exploratory and later held-out windows before choosing parameters; report every variant tried, sample counts and uncertainty. A diagnostic with insufficient eligible trades is inconclusive.
- Report rule hits → data-quality/spread/volume suppressions → candidates → risk rejections (especially expectancy) → executable trades. Separate per-symbol/UTC-hour/weekday-weekend results and warm-up, missing horizons and synthetic bars. Do not infer historical spread/executability from OHLCV alone; historical quote coverage is a limitation unless captured separately.
- Use the current account's fee tier, spread, adverse slippage/gap scenarios and **all** LLM costs, including rejected cycles and reviewer spend. Normalize fixed costs to the intended ~1,000 EUR account scale using a recorded USD conversion; also show the actual paper balance. Forward return is a signal diagnostic, not a realized stop/TP execution backtest.
- At `p = 0.50`, TP = 2R and 25 bps per leg, the check as it was before WP 1.R1b gave `EV / (qty × entry) = 0.495 × (R / entry) − 0.005`: positive EV needed stop distance > **1.0101%** of entry (ATR > **0.6734%** for the 1.5 ATR stub stop, before tick effects). **Current check (WP 1.R1b, 2026-10-12):** check 11 uses the D16 cash-flow model, `ev = qty × (p × pnl(tp) − (1 − p) × L)` (SPEC §4.5), with the profile's 10 bps exit slippage applied to TP and stop. With the same p, TP and fees, positive EV now needs stop distance > **1.2037%** of entry for USD buy fees (`quote`, SimBroker) or > **1.2050%** for coin buy fees (`base`, Alpaca); ATR > **0.8025%** / **0.8033%**. This is a cost floor, not a recommendation to widen a stop or weaken the check. Stop slippage and LLM spend make the practical hurdle higher.
- Record a retain/change/inconclusive decision before Phase 2 spends money on the chosen profile. Proposed risk/universe/timeframe changes need human approval and a new profile hash; do not relax risk checks to manufacture trades. Keep the Phase 1 end-to-end acceptance gate distinct from a positive-economic-evidence gate for live operation.
