## 2. Tech baseline (Phase 0 decisions)

- Python 3.12, **uv** for env/lock, `src/` layout, ruff + mypy (strict on `risk/`, `broker/`, `core/`), pytest + hypothesis + pytest-asyncio, coverage gate on `risk/` = 100 % branches.
- SQLAlchemy 2.x async (`aiosqlite` dev, `asyncpg` prod), Alembic with `render_as_batch=True` (SQLite ALTER limitations). JSON columns via SQLAlchemy `JSON` type (portable).
- Pydantic v2 for all domain types; shared between core, API, and agent schemas.
- structlog JSON, `cycle_id` bound via contextvars.
- `alpaca-py` for REST + WS; `anthropic` SDK directly, no agent framework.
- Money/qty: `Decimal` in Risk Engine, broker adapter and journal; floats only inside indicator math.
- Single asyncio process for core; API as separate process reading the same DB and writing `control_state` + kill file.
- CI: GitHub Actions — ruff, mypy, pytest (unit + SimBroker integration with recorded fixtures), `pip-audit`.

### 3.2 Position management and recovery acceptance (WP 1.5–1.6)

1. **Safe startup:** acquire journal ownership, validate account/mode, recover cycle records, reconcile broker orders/fills/positions, restore exit state and act on overdue exits, then allow candidate admission. `recover()` alone only repairs cycle bookkeeping; it does not reconcile holdings. A failure keeps entries disabled while protective exits remain available when position/mode can be established. WP 1.5 wires this against SimBroker; real Alpaca admission additionally needs WP 1.6.
2. **Exit contract:** persist original stop, TP, initial risk, holding deadline and trailing high-water state before they can be lost to a restart. The current stub has no hold-time field: use the profile's `risk.max_hold_min` for Phase 1; Phase 2 validates/clamps the agent request. Define executable trigger prices, precedence when several exit reasons fire, conservative same-bar stop/TP handling, and retry/dust handling. Protect any acquired qty immediately; a partial fill cannot wait for the rest of the order before getting a stop.
3. **Order reconciliation is broader than open cycles or open-status rows:** cover `pending`, `unknown`, `new`, plus final broker statuses whose fills/position effects have not yet been durably applied. WP 1.3 `_refresh_open_entries()` can already set an entry row to `filled`/`canceled`; excluding these rows would lose the handoff. `canceled` can include positive fills; terminal `ERROR` cycles can own real orders. Use one atomic/idempotent journal update per fill/effect; replay/restart produces the same quantities and P&L. Never reopen a terminal cycle just to reconcile its order.
4. **Absence is not proof:** use entry client ids; for legacy id-less exits use bounded symbol/side/time/qty matching over complete history, excluding orders already linked elsewhere. One uniquely proven match links; ambiguity pauses and alerts. A zero-match result after a grace period is **not sufficient** for `not_submitted`: a timed-out SDK worker or delayed broker visibility can still produce an order. Keep uncertainty/reservations until the original request cannot still submit and authoritative broker evidence resolves it, or require operator resolution. This supersedes the earlier grace-window-only wording in the historical D14 notes.
5. **Kill/flatten:** latch entry admission first, cancel outstanding entries through the Risk Engine, reconcile cancellation races, request audited reduce-only exits, and continue handling late fills. Do not cancel protective sell orders as if they were entries. Completion means no sellable holdings and no unresolved entry capable of filling; dust/uncertainty must be reported, not silently counted as flat. Exit retries reread both position and unresolved close attempts; a passing SimBroker reservation test is not proof of Alpaca behavior.
6. **Accounting required in Phase 1:** write positions and estimated fee-adjusted realized P&L on close, so the existing Risk Engine's `strategy_trade_stats()` eventually leaves its prior using meaningful data. Keep initial-risk denominator immutable when trailing. Broker fee deductions explain only their bounded difference; any unexplained quantity/P&L discrepancy pauses entries. Posted fee-activity replacement, MAE/MFE, attribution and dashboard reporting remain 3.1. Provisional-vs-final fee status and activity identities must prevent double charging and support later corrections.
7. **Shutdown:** close admission, stop new feed work, drain/force-cancel runner under its budget, drain the bus, then release resources; keep the documented process watchdog/second-signal hard deadline. Record abandoned work for recovery. Do not call forced cancellation proof that broker work stopped. A persistent fill identity is needed by 1.5's interface/tests and implemented for Alpaca in 1.6.

### 3.3 Strategy evaluation and evidence (WP 1.7)

The owner requested strategy alternatives for review; SPEC §16.1 proposes a BTC-only, slower-signal candidate with lower exposure and LLM spend. It is a proposal, not an approved replacement profile or a claim of profitability.

- Compare the current baseline and named candidate variants on the **same time-ordered data**, with identical fee, slippage and fill assumptions. Split exploratory and later held-out windows before choosing parameters; report every variant tried, sample counts and uncertainty. A diagnostic with insufficient eligible trades is inconclusive.
- Report rule hits → data-quality/spread/volume suppressions → candidates → risk rejections (especially expectancy) → executable trades. Separate per-symbol/UTC-hour/weekday-weekend results and warm-up, missing horizons and synthetic bars. Do not infer historical spread/executability from OHLCV alone; historical quote coverage is a limitation unless captured separately.
- Use the current account's fee tier, spread, adverse slippage/gap scenarios and **all** LLM costs, including rejected cycles and reviewer spend. Normalize fixed costs to the intended ~1,000 EUR account scale using a recorded USD conversion; also show the actual paper balance. Forward return is a signal diagnostic, not a realized stop/TP execution backtest.
- At `p = 0.50`, TP = 2R and 25 bps per leg, the current check gives `EV / (qty × entry) = 0.495 × (R / entry) − 0.005`: positive EV needs stop distance > **1.0101%** of entry (ATR > **0.6734%** for the 1.5 ATR stub stop, before tick effects). This is a cost floor, not a recommendation to widen a stop or weaken the check. Stop slippage and LLM spend make the practical hurdle higher.
- Record a retain/change/inconclusive decision before Phase 2 spends money on the chosen profile. Proposed risk/universe/timeframe changes need human approval and a new profile hash; do not relax risk checks to manufacture trades. Keep the Phase 1 end-to-end acceptance gate distinct from a positive-economic-evidence gate for live operation.
